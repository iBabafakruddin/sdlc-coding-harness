# Codebase onboarding (Tech Lead)

Goal: every agent can read `.sdlc/project-profile.md` and know how this project is built, tested and structured — without re-discovering it each time.

## 1. Survey (read-only)
- Root and workspace (`project.workspace` in `.sdlc/config.json`): manifests (`package.json`, lockfiles, `pyproject.toml`, `requirements*.txt`, `pom.xml`, `build.gradle`, `go.mod`, `*.csproj`, `Cargo.toml`), monorepo markers (`pnpm-workspace.yaml`, `turbo.json`, `nx.json`), `Dockerfile`, `docker-compose*`.
- Existing CI (`.github/workflows`, `.gitlab-ci.yml`, `azure-pipelines.yml`, `Jenkinsfile`) — **the CI's commands are the best source of truth** for lint/test/build.
- `README`, `CONTRIBUTING`, existing `CLAUDE.md` content outside the harness block.
- Source layout, entry points, routing, data access, config/env handling (`.env.example`).
- Tests: framework, location, naming, how they're run, coverage setup, fixtures/factories.
- Lint/format config (`.eslintrc*`, `eslint.config.*`, `.prettierrc`, `ruff.toml`, `.editorconfig`), commit conventions (commitlint, husky).
- Git: `git log --oneline -20` (commit style), `git branch -a` (branch naming in use), default branch.

**Empty project** (no code yet) — greenfield path:
- record "greenfield" and the *intended* stack (respect `project.tech_stack`; runtimes on their **current LTS**, never an EOL version) and *intended* commands in the profile, each marked `not run (greenfield)`;
- leave `project.commands` empty (the gate auto-detects from `package.json` / `pyproject.toml` meanwhile);
- plan for the gate's static checks: a logger module instead of `console.log`/`print`, fixture helpers for test credentials, coverage as json-summary;
- note that the first groomed story must be a scaffold story that sets them up (see `story-grooming`), and that you re-run this skill after the scaffold's REQ is integrated into main (workflow §10): then run each command, fill `project.commands`, replace "greenfield" in the profile.

## 2. Determine and verify commands
Pick the exact commands, run each **once** from the workspace, note duration and result:
| key | examples |
|---|---|
| install | lockfile-respecting only: `npm ci`, `pnpm install --frozen-lockfile`, `yarn install --frozen-lockfile`, `pip install -e .[dev]`, `./gradlew dependencies` (never plain `npm install`: it hides lockfile drift) |
| lint | `npm run lint`, `ruff check .`, `./gradlew check -x test` |
| typecheck | `npx tsc --noEmit`, `mypy src` |
| test | must produce coverage the gate can read: jest/vitest with `--coverage --coverageReporters=json-summary` → `coverage/coverage-summary.json`; pytest with `--cov --cov-report=json:coverage.json` |
| build | `npm run build`, `python -m build`, `./gradlew assemble` |

If a command fails on a clean main branch, record it under **Known issues** (pre-existing failures are not the developers' fault) and tell the human. If the project's coverage format isn't one of the two the gate reads, add a coverage command to the test step that produces one, or set `quality_gates.coverage_min` to 0 and say so.

Write them into `.sdlc/config.json → project.commands` (empty string = not applicable), and `project.tech_stack` as a short phrase.

## 3. Write `.sdlc/project-profile.md`
```markdown
# Project profile
_Generated by codebase-onboarding on <date>. Re-run /sdlc-init when the stack changes._

## Stack
## Structure            (top-level map: folder → purpose; entry points)
## Conventions          (naming, file layout, state mgmt, error handling, API style, commit style)
## Commands             (table: key | command | verified result | duration)
## Testing              (framework, where tests live, naming, fixtures, how to run one test)
## Configuration & secrets (env vars, .env.example, never commit .env)
## CI                   (existing pipelines and what they run)
## Known issues         (pre-existing failures, flaky tests, tech debt hotspots)
## Do-not-touch areas   (generated code, vendored libs, migrations history, ...)
```
Keep it factual and under ~150 lines; link to files instead of copying them.

## 4. Report
Stack, verified commands (pass/fail), coverage readability, known issues, and anything the human must decide (e.g. "no test runner — first sprint needs a scaffold story").
