# harness-telugu — reusable agile team of Claude sub-agents

Mana team lo humans chese pani (BA → Tech Lead grooming → Scrum Master sprint planning →
Developers on their own branches → PR review → CI/quality gates → merge → QA build → QA testing →
bug fix → retro) ippudu sub-agents chestayi. Jira badulu `.sdlc/board/` lo local markdown tickets.

This folder is a **template**: install it into any new or existing project.

## Install into a project
```bash
python install.py D:/projects/my-app             # new folder or existing repo
python install.py D:/projects/my-app --dry-run   # preview first
```
Then in that project:
```bash
python .sdlc/tools/board.py init                  # board (+ git repo & first commit if the folder isn't a repo yet)
git add .claude .sdlc CLAUDE.md .gitignore && git commit -m "chore: add SDLC agent harness"   # existing repos
```
Open Claude Code in the project and run:
```
/sdlc-init                                         # tech-lead onboards the codebase: stack, conventions, verified test/lint/build commands
/sdlc-feature I need a login page with email and password
```

**Upgrade** a project later: run the same `install.py` command again. `.sdlc/manifest.json` tracks installed files, so
files you changed locally are kept (use `--force` to overwrite, a `.bak` is made), your own files with the same name are never touched,
and `.sdlc/config.json` keeps your values (new keys get merged in). `--uninstall` removes unmodified harness files and the CLAUDE.md/.gitignore blocks.

What install touches in the target: `.claude/agents/` (8 files), `.claude/skills/` (13 skills), `.sdlc/`, a marked block in `CLAUDE.md`,
a marked block in `.gitignore`, and a marked `.gitattributes` block (only if the project has no `.gitattributes` of its own). Nothing else in your project.

## Branch per feature, branch per developer
```
main ─────●──────────────────────────────────●────────► qa/SPRINT-01 (QA build)
          └─► feature/REQ-001-login-page ─●──●──●       ▲ feature PR after all stories merged
                   ├─► story/STORY-001 ───┘     │   dev-1 · own worktree
                   └─► story/STORY-002 ─────────┘   dev-2 · own worktree
QA bugs: main ─► bugfix/BUG-001-… ─► PR ─► main
```
- Every requirement gets `feature/REQ-…` from main; every story gets `story/STORY-…` from the feature branch.
- Each story branch is checked out in **its own git worktree** (`../<repo>-worktrees/STORY-…`), so developer agents run in parallel without touching each other's files. The main checkout always stays on main.
- Story PRs go into the feature branch; when the feature is complete a feature PR (gate + integration review) goes into main.
- All of it via `python .sdlc/tools/git_flow.py` (`feature-start`, `start`, `sync`, `merge`, `finish`, `qa-build`, `status`).
- Several related requirements? Shared groundwork goes in a **foundation REQ** that is integrated into main first: a story can't use another REQ's code before that (`git_flow.py start` refuses).
- Prefer the simpler model? Set `git.strategy` to `"story"` (story branches straight off main).

## Commands
| Command | What it does |
|---|---|
| `/sdlc-init` | Onboard the project: board, `.sdlc/project-profile.md`, verified build/test commands, branching check |
| `/sdlc-feature <request>` | Full lifecycle; add `until groomed` / `until merged` / `until qa` to stop early |
| `/sdlc-sprint [SPRINT-xx]` | Plan a sprint from the backlog or resume one |
| `/sdlc-status` | Standup + board + branches + decisions needed |

## What's where (inside a project)
| Path | Purpose |
|---|---|
| `.sdlc/process/workflow.md` | Process rules: roles, state machines, DoR/DoD, branching model, loop limits |
| `.sdlc/config.json` | Team & capacity, git strategy & worktree folder, approval gates, loop limits, gate thresholds, project commands |
| `.sdlc/project-profile.md` | Generated by `/sdlc-init`: stack, structure, conventions, commands, known issues |
| `.sdlc/tools/board.py` | Local Jira: tickets, guarded status moves, activity log, capacity, metrics, `BOARD.md` |
| `.sdlc/tools/git_flow.py` | Feature/story/bugfix branches + worktrees, sync, no-ff merges, QA branch, cleanup |
| `.sdlc/tools/quality_gate.py` | Local CI + Sonar stand-in, runs inside the branch's worktree |
| `.sdlc/templates/` | Ticket templates (REQ, STORY, BUG, PR, SPRINT, QA) |
| `.sdlc/board/` | Tickets + `BOARD.md` + gate reports (git-ignored, like Jira lives outside git) |
| `.claude/agents/` | business-analyst, tech-lead, scrum-master, developer, code-reviewer, security-reviewer, devops-engineer, qa-engineer |
| `.claude/skills/` | One playbook per role + `codebase-onboarding` + orchestrators |

## Board & branch cheatsheet
```bash
python .sdlc/tools/board.py list --sprint SPRINT-01
python .sdlc/tools/board.py show STORY-001
python .sdlc/tools/git_flow.py status
python .sdlc/tools/git_flow.py start STORY-001 --dev dev-1
python .sdlc/tools/quality_gate.py --pr PR-001
```
```bash
python .sdlc/tools/board.py section STORY-001 "Developer analysis" --file analysis.md --by dev-1
python .sdlc/tools/board.py comment PR-001 --by code-reviewer --sev major --loc src/auth.ts:42 --text "use the hash helper"
python .sdlc/tools/board.py resolve PR-001 C1 fixed --by dev-1
python .sdlc/tools/board.py verdict PR-001 approved --by code-reviewer --note "LGTM"
python .sdlc/tools/board.py metrics          # committed / dev-complete / done per sprint
python .sdlc/tools/board.py export           # zip backup of the (git-ignored) board
```
The board refuses process violations, e.g. READY without a filled Definition of Ready (every section, ≤ 8 points,
`security` label when auth words appear), a GROOMED REQ without linked stories, IN_PROGRESS without the ticket's branch,
a PR whose branch/base don't match the ticket, PR APPROVED with a failed gate or open blocker/major comments, a PR to main
with *any* open comment, a story start that needs another REQ's code not yet in main, DONE with an open major bug.
All writes are locked, so parallel agents never overwrite each other. The tools refuse to run on the template folder itself.

## Built-in improvements
- Guarded state machine (Definition of Ready/Done and review rules enforced by code)
- Security reviewer auto-joins PRs of stories labelled `security`
- Human approval gates (`after_grooming`, `before_merge_to_main`, `before_qa_release`)
- Review/QA loop limits that escalate to you
- Traceability REQ → feature branch → STORY → story branch/commits `[STORY-x]` → PR → TC → BUG
- Parallel developers in isolated worktrees, dependency waves
- Codebase onboarding profile so agents follow your project's conventions and real CI commands
- ADRs, spike stories, retro metrics → process improvements
- Pluggable CI: `quality_gates.extra_commands` (e.g. SonarQube), `workflow.pr_mode: "github"` for real PRs

## Optional settings
`.sdlc/setup/claude-settings.example.json` pre-approves the harness commands, denies force-push/hard-reset and re-renders the
board after edits. Review it and merge it into the project's `.claude/settings.json` yourself if you want fewer permission prompts.
